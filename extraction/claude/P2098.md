## Objetivo

Propor e avaliar um framework proativo, "all-in-one" e orientado a dados que integra dados de task management e issue tracking do Jira com atividade de codigo do GitHub para prever o risco de burnout de desenvolvedores. O estudo extrai metricas multimodais do dataset Mozilla–Apache (20-MAD), treina e compara modelos de machine learning, identifica os preditores mais associados ao risco de burnout e apresenta um prototipo de dashboard com interface em linguagem natural para monitorar esse risco.

## Frameworks e Metricas

### Frameworks Referenciados
- **Burnout Assessment Tool (BAT)** — REFERENCED (exhaustion, mental distance, cognitive impairment, emotional impairment); nao aplicado diretamente, mas o proxy foi "conceptually aligned with the BAT".
- **Maslach Burnout Inventory (MBI)** — REFERENCED (emotional exhaustion, depersonalization, reduced personal accomplishment).
- **Job Demands-Resources (JD-R)** (Demerouti & Sanz Vergel) — REFERENCED como justificativa para o maior peso de workload intensity.
- **Valence–Arousal–Dominance (VAD)** para comentarios do Jira — REFERENCED.
- **Risk-based burnout modeling** [13] — REFERENCED (alinhado ao score composto).
- **Best-practice ontology de 40 praticas em issue tracking** [4] — REFERENCED.
- **GitHub teamwork styles (toilers, communicators, collaborators)** — REFERENCED.
- Nenhum framework de produtividade (DORA, SPACE, DevEx) e citado.

### Frameworks Propostos
Framework multimodal de predicao de burnout em sete fases: coleta (20-MAD), preprocessamento e feature engineering (merge Jira–GitHub por issue identifiers, rolling temporal windows), modelo preditivo com label proxy Bd/Ld, teste e avaliacao (varios classificadores), dashboard em tempo real (React–Vite + backend Python, risco em percentual), NLP interface baseada em LLM para consultas e recomendacoes, e testes unitarios/de integracao do sistema.

## Fatores que Influenciam Produtividade

### Fatores Positivos
| Fator | Categoria |
|-------|-----------|
| Equilibrio entre coding e collaboration (citando estudo de work styles no GitHub) | Human / Process |
| Priorizacao automatizada de issues para reduzir cognitive overload (citado) | Technical / Process |
| Deteccao precoce de burnout por analytics de repositorio "before it leads to loss in productivity" | Organizational |

### Fatores Negativos
| Fator | Categoria |
|-------|-----------|
| Alta intensidade de commits e volume de linhas alteradas (associados a maior risco de burnout) | Human / Process |
| Alto volume de issues atribuidas | Organizational / Process |
| Trabalho fora do horario (early-morning, late-night, weekend) | Human |
| Context switching entre componentes/modulos (unique components) | Process |
| Transicao para agile com alta pressao e iteracoes curtas (citado como causa de burnout) | Process / Organizational |
| Pull requests nao mergeados (~40%) gerando frustracao (citado) | Process |
| Burnout causa perda de produtividade e turnover ($125–195 bilhoes/ano, citado) | Human / Organizational |

## Resultados Principais

- ANN (MLP) teve o melhor desempenho: accuracy 98.48%, precision 97.92%, recall 96.90%, F1-score 97.41%.
- Os seguintes foram XGBoost (97.82% accuracy; F1 96.27%), Stacking Ensemble (97.34%; 95.46%), Voting Ensemble (97.31%; 95.33%) e AdaBoost (96.68%; 94.19%); Decision Tree foi o pior (90.53%; F1 83.32%).
- Preditores com maior correlacao de Spearman com o risco de burnout: commits_count (0.519), total_lines_changed (0.486), issues_count (0.454), early_morning_commits (0.361), unique_components (0.324), late_night_commits (0.295), average_lines_changed (0.293), unresolved_issue_ratio (0.196), weekend_work_ratio (0.138), high_priority_ratio (0.088), average_issue_age (0.030), average_commit_time (−0.102).
- Os autores afirmam que integrar Jira e GitHub "may produce better predictive performance than analyzing each data source independently", mas nao reportam comparacao quantitativa com fontes isoladas.
- Foi construido um prototipo de dashboard com o ANN e uma NLP interface que da recomendacoes de mitigacao.

## Desafios do Uso das Metricas

- Nao ha anotacoes de burnout validadas: o label e um proxy teorico com pesos arbitrarios ("transparent modeling assumptions") e limiar de 0.5, nao equivalente a instrumentos como BAT.
- Abordagens tradicionais por survey (MBI, BAT) sao reativas, retrospectivas e subjetivas, inadequadas para monitoramento continuo; abordagens de fonte unica (so Jira ou so GitHub) nao capturam a relacao entre tarefas atribuidas e desenvolvimento real.
- Metricas de atividade (commits, lines changed) passam a ser lidas como sinais de risco de burnout, e nao apenas de produtividade.
- Dados open source diferem de ambientes industriais, o que limita a generalizacao.

## Limitacoes

- Estudo com o dataset open source Mozilla–Apache (20-MAD), portanto "the external validity is limited"; nao e um estudo direto de times industriais Scrum/Kanban.
- Os indicadores de burnout derivados do repositorio nao tem mecanismo de ponderacao validado e nao equivalem a instrumentos convencionais como o BAT; pesos e limiar sao suposicoes operacionais.
- Dashboard depende de dados inseridos; a integracao em tempo real via APIs do Jira e GitHub e trabalho futuro, assim como a validacao em ambientes industriais e algoritmos de realocacao de tarefas.

## Contribuicao Principal

O paper propoe um framework de predicao de burnout que integra dados de issue tracking (Jira) e de atividade de codigo (GitHub) usando um score proxy multidimensional (workload intensity, irregularidade, task complexity, context switching), em vez de surveys ou de uma unica fonte. Em dados do 20-MAD, um ANN alcancou 98.48% de accuracy e 97.41% de F1 na predicao do label proxy. Volume de commits, linhas alteradas, issues atribuidas, trabalho fora de horario e context switching foram os preditores mais associados ao risco. O trabalho tambem entrega um prototipo de dashboard com NLP interface para monitoramento, como base inicial para validacao futura em ambientes industriais.
