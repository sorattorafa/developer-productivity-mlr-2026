## Objetivo

Ir alem da avaliacao de hallucinations de LLMs como problema dicotomico de correcao e propor um modelo sistematico para avaliar o impacto de hallucinations (fabricated APIs, incorrect parameters, non-existent libraries) em workflows de desenvolvimento assistido por IA no estilo vibe coding, ligando-as a developer throughput, defect density, rework cycles e architectural erosion, e demonstrar o modelo com dados sinteticos calibrados pela literatura, discutindo estrategias de mitigacao para AI-native IDEs.

---

## Questoes de Pesquisa

- RQ1: "how do particular types of hallucinations in AI-assisted code generation influence the productivity of developers, code quality, and technical debt in vibe coding work-flows?"

## Frameworks e Metricas

### Frameworks Referenciados
- **Taxonomia de API misuse em codigo gerado por LLM (Kang, Hwang e Yoo, MSR 2024) [5]** — APPLIED (base da taxonomia de hallucinations, da deteccao de misuse e da calibracao do dataset sintetico).
- **"Multi-dimensional productivity frameworks"** adotados por estudos da SLR [3] — REFERENCED (sem nomear frameworks especificos).
- **Desenhos experimentais randomizados/comparativos de estudos anteriores [3, 4]** — REFERENCED (base do within-subject design).
- DORA, SPACE, DevEx, GQM — nao mencionados.

### Frameworks Propostos
- **Taxonomia de hallucinations para vibe coding (Table I)**: Fabricated APIs (metodos/classes/campos inventados → compilation errors, missing symbol); Incorrect Parameters (parametros inexistentes, errados ou ausentes → runtime faults, subtle logic bugs); Non-Existent Libraries (pacotes/imports imaginarios → dependency errors, supply-chain risk).
- **Modelo multidimensional de impacto (Secao IV)**: liga tipos de hallucination a metricas de productivity, code quality e technical debt.
- **Conceptual Impact Model (Figure 1)**: "hallucination at suggestion time → developer acceptance → immediate failures or latent defects → rework and architectural adjustments"; hallucinations "shape developer behavior (e.g., over-reliance, trial-and-error debugging)".
- **Impact-sensitive evaluation**: acompanhar taxas de API misuse e tipos de hallucination ao longo do tempo; correlacionar intensidade de uso dos assistentes com defect density e rework ratios; incluir medidas hallucination-conscious em developer experience surveys e avaliacao de ferramentas.

## Fatores que Influenciam Produtividade

### Fatores Positivos
| Fator | Categoria |
|-------|-----------|
| Assistentes LLM reduzem overhead de inicio de tarefas e aceleram code completion (literatura citada) | Technical |
| AI-native IDEs com "3-5x enhancements" em atividades tipicas (setups, settings, boilerplate), sobretudo em prototipagem | Technical |
| Hallucinations "produtivas" (sugestoes especulativas que inspiram opcoes de design ou revelam APIs nao obvias), sob supervisao critica | Technical / Human |
| Mitigacoes: API grounding, inline validation, confidence visualization, guardrail prompts, planned validation steps, adaptacao por tipo de tarefa | Technical / Process |

### Fatores Negativos
| Fator | Categoria |
|-------|-----------|
| Hallucinations (fabricated APIs, incorrect parameters, non-existent libraries) aumentam iteracoes e context switches | Technical |

| Over-reliance e trial-and-error debugging | Human |
| Baixo desempenho em codebases grandes e baixa confiabilidade do codigo gerado (estudo citado com ~19% de reducao de produtividade) | Technical |

## Resultados Principais

(Todos os resultados sao declarados "synthetic, calibrated" — "empirically motivated but synthetic findings", em linha com a literatura [3, 5, 7].)

- Distribuicao exemplo de hallucinations em sessao hallucination-rich (Table II): Fabricated APIs 35%, Incorrect Parameters 40%, Non-existent Libraries 25% dos misuses.
- Produtividade (Table III): Baseline AI-assisted — mediana 30 min, 4 iteracoes/tarefa, 3 context switches/tarefa; Hallucination-rich AI — 26 min, 6 iteracoes, 5 context switches. Interpretacao: "a minor decrease in median task time but a higher count and context switches".
- Qualidade (Table IV): Baseline — test pass rate 92%, defect density 0.8 defects/KLOC, 0.5 API hallucination misuses/task; Hallucination-rich — 84%, 1.4, 2.1. Indica trade-off entre throughput e confiabilidade.
- Technical debt (Table V): Baseline — rework ratio 18%, 1.2 new dependencies per 10 tasks, latent defect risk 1.0 (relativo); Hallucination-rich — 31%, 2.6, 1.8.
- Conclusao: "hallucination-intensive help may boost the short-term throughput at the cost of code quality and technical debt"; hallucinations sao "structural forces that transform the work process of developers".
- Mitigacoes propostas: API-grounded generation, inline validation, confidence visualization; guardrail prompts (pedir citacoes, referencias de documentacao, test stubs), planned validation steps, type-based adaptation (mais escrutinio em codigo de seguranca/infraestrutura).

## Desafios do Uso das Metricas

- Tratar hallucinations apenas como problema dicotomico de correcao ("accuracy measures only") e insuficiente; e preciso olhar efeitos no nivel do workflow.
- Ganhos de throughput podem correlacionar negativamente com qualidade (estudo citado [7] com "moderate negative correlation"), logo metricas de qualidade devem ser consideradas junto com velocidade.
- Technical debt "is more difficult to measure directly"; os autores recorrem a proxies (rework ratio, architectural erosion, latent defect risk).
- Hallucinations podem gerar codigo sintaticamente correto mas semanticamente defeituoso, dificil de detectar por testes rasos e inspecao manual.
- Acesso a logs proprietarios de uso em larga escala e limitado, o que motivou o uso de dados sinteticos.

## Contribuicao Principal

O artigo propoe uma visao de hallucinations de LLMs em vibe coding como fenomeno de workflow, e nao apenas de correcao, oferecendo uma taxonomia de tres tipos (fabricated APIs, incorrect parameters, non-existent libraries), um modelo conceitual de propagacao do impacto e um conjunto de metricas de productivity (task completion time, iteration count, context switches), code quality (test pass rate, defect density, static-analysis warnings, API-misuse rates) e technical debt (rework ratio, architectural erosion, new dependencies, latent defect risk). Resultados sinteticos calibrados ilustram que hallucinations podem aumentar levemente o throughput de curto prazo enquanto degradam qualidade e acumulam divida tecnica. O artigo tambem sugere mitigacoes para AI-native IDEs e a inclusao de medidas hallucination-conscious em developer experience surveys.
